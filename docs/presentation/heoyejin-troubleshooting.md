# 백엔드 트러블슈팅 정리

발표에서 예진님이 직접 설명할 수 있는 주제만 정리한 문서입니다.

> 아래 내용은 운영 장애를 과장하지 않고, 구현 과정에서 발견한 위험과 테스트로 검증한 해결을 중심으로 작성했습니다.

## 1. Refresh Token 재발급과 토큰 저장 문제

### 문제

로그인·재로그인·재발급을 반복할 때 다음 문제가 생길 수 있었습니다.

1. JWT에 발급 시각만 사용하면 같은 사용자가 같은 초에 발급받은 토큰이 동일해질 수 있었습니다.
2. 로그아웃 직후 다시 로그인했을 때, 폐기한 Refresh Token과 같은 값이 다시 발급될 가능성이 있었습니다.
3. 재발급과 로그아웃이 동시에 실행되면, 한쪽이 다른 쪽의 토큰 상태를 덮어쓸 수 있었습니다.
4. Refresh Token 원문을 DB에 저장하면 DB가 노출됐을 때 바로 재사용될 수 있었습니다.

### 원인

토큰 자체의 유일성과 DB에 저장된 토큰 상태의 동시성 제어가 분리되어 있었습니다.

- JWT의 사용자 ID와 만료 시각만으로는 같은 시점의 토큰을 구분할 수 없습니다.
- Refresh Token 조회, 검증, 교체가 서로 다른 작업으로 실행되면 같은 토큰을 여러 요청이 동시에 사용할 수 있습니다.
- 로그아웃과 재발급이 같은 사용자의 Refresh Token 행을 동시에 변경할 수 있습니다.

### 해결

#### 1) 토큰마다 `jti` 발급

`JwtProvider.generateToken()`에서 토큰을 발급할 때마다 UUID 기반 `jti`를 추가했습니다.

```text
같은 사용자 + 같은 시각에 발급
→ 서로 다른 jti
→ 서로 다른 access token / refresh token
```

따라서 로그아웃 직후 재로그인해도 폐기된 Refresh Token 값이 다시 발급되지 않습니다.

#### 2) DB에는 Refresh Token 원문 대신 SHA-256 해시 저장

클라이언트에 반환한 원문은 서버 DB에 저장하지 않고 SHA-256 해시만 저장합니다.
재발급 요청이 들어오면 다음 순서로 확인합니다.

```text
요청 Refresh Token
→ JWT 서명·만료·type·jti·sub 검증
→ 요청 토큰을 SHA-256 해시
→ 사용자별 DB 해시와 비교
→ 성공하면 새 access token과 새 refresh token을 함께 발급
```

#### 3) Refresh Token 회전과 사용자 행 잠금

재발급 성공 시 기존 Refresh Token을 유지하지 않고 access token과 Refresh Token을 모두 교체합니다.

로그인, 로그아웃, 재발급은 모두 사용자 행을 먼저 잠그도록 통일했습니다.

```text
users 행 잠금
→ refresh_tokens 조회·검증
→ 토큰 삭제 또는 교체
→ 트랜잭션 커밋
```

동일한 Refresh Token으로 동시에 재발급 요청이 들어오면 한 요청만 성공하고, 나머지는 이미 교체된 토큰으로 판단하여 `401 REFRESH_TOKEN_INVALID`를 반환합니다.

#### 4) 실패 시 기존 상태 보존

새 토큰 발급에 실패하면 기존 Refresh Token을 먼저 삭제하지 않습니다. 발급과 저장이 실패한 경우에도 기존 토큰을 유지하여 다시 재발급할 수 있게 했습니다.

### 검증

`TokenRefreshApiTest`와 JWT 단위 테스트로 다음을 검증했습니다.

- access token과 Refresh Token의 `jti`가 매 발급마다 다름
- 정상 재발급 시 두 토큰이 모두 교체됨
- 이전 Refresh Token 재사용 거부
- 만료·변조·잘못된 token type·필수 claim 누락 거부
- DB에 저장되지 않은 토큰과 재로그인으로 교체된 토큰 거부
- 로그아웃 이후 기존 토큰과 회전된 토큰 거부
- 동일 토큰 동시 요청 6건 중 1건만 성공
- 로그아웃과 재발급 동시 실행 후 저장된 Refresh Token이 남지 않음
- 전체 테스트 **498개 통과 / 실패 0개 / 오류 0개**

### 발표용 설명

> “Refresh Token은 단순히 JWT를 새로 발급하는 API로 만들지 않았습니다. 같은 토큰의 재사용과 동시 요청을 막기 위해 발급마다 `jti`를 넣고, DB에는 원문이 아닌 해시를 저장했습니다. 재발급·로그아웃·로그인을 사용자 행 잠금과 하나의 트랜잭션 규칙으로 직렬화해, 같은 토큰이 동시에 들어와도 한 번만 성공하도록 했습니다.”

### 남은 정책

- 현재 사용자는 Refresh Token을 하나만 가집니다. 여러 기기별 세션은 지원하지 않습니다.
- Access Token은 로그아웃 즉시 폐기하지 않고 만료 시각까지 유효합니다.
- 서버가 토큰 회전에 성공했지만 응답이 네트워크에서 유실되면, 클라이언트는 이전 Refresh Token을 재사용할 수 없으므로 다시 로그인해야 합니다.

## 2. AdMob 보상형 광고 SSV 중복 지급 방지

### 문제

앱에서 광고를 끝까지 봤다는 콜백만으로 슬롯을 지급하면 서버가 보상 사실을 신뢰할 수 없습니다.

- 클라이언트 콜백은 변조될 수 있습니다.
- Google이 같은 SSV 콜백을 재전송할 수 있습니다.
- 같은 세션에 서로 다른 거래 ID가 도착할 수 있습니다.
- 콜백 처리와 슬롯 증가가 따로 실행되면 한쪽만 성공할 수 있습니다.
- 광고 단위나 보상량이 다른 콜백을 그대로 처리하면 잘못된 지급이 발생합니다.

### 원인

광고 시청 UI의 이벤트와 Google 서버가 보내는 보상 검증 이벤트는 서로 다른 신뢰 경계에 있습니다.

따라서 다음을 모두 확인해야 합니다.

```text
Google 서명
+ 서버가 발급한 시청 세션
+ 플랫폼별 광고 단위
+ 보상 종류와 보상량
+ 거래 ID 중복 여부
+ 사용자·일일 한도·세션 상태
```

### 해결

#### 1) 앱 콜백이 아니라 Google SSV를 지급 기준으로 사용

앱의 `onUserEarnedReward` 콜백은 화면에 “보상 확인 중”을 표시하는 용도로만 사용합니다.
실제 슬롯 증가는 Google이 서버로 보낸 SSV 콜백을 검증한 뒤에만 수행합니다.

```text
앱 → 서버: 광고 시청 세션 발급
서버 → 앱: sessionId와 customData 반환
앱 → AdMob: customData를 포함해 광고 표시
Google → 서버: 서명된 SSV 콜백
서버: 검증 후 슬롯 +2
앱 → 서버: 세션 결과 조회
```

#### 2) 원문 query string을 대상으로 서명 검증

SSV의 서명 검증 전에 query string을 임의로 decode하거나 다시 조합하지 않습니다.
원문 query string을 Tink `RewardedAdsVerifier`에 전달하고, 공개키 조회 실패와 서명 불일치를 서로 다른 실패로 처리합니다.

- 서명 불일치·잘못된 파라미터: 지급하지 않고 `400`
- 공개키 조회 등 일시적 검증 장애: 성공으로 처리하지 않고 `503`
- query string이 없는 콜백: 지급하지 않고 잘못된 요청으로 처리

#### 3) 서버 발급 세션과 콜백 연결

앱이 정한 사용자 ID나 보상량을 신뢰하지 않고, 서버가 발급한 `customData`의 세션을 기준으로 지급 대상을 찾습니다.

콜백에서는 다음 값을 세션에 저장된 정책과 비교합니다.

- 플랫폼별 기대 광고 단위
- `reward_item = recipe_slot`
- 세션에 저장된 보상량 `2`
- 세션 상태 `PENDING`
- 세션 만료 및 검증 마감
- 활성 사용자와 해당 날짜의 일일 지급 한도

#### 4) 중복 지급을 DB와 트랜잭션으로 방어

지급 트랜잭션에서는 다음 잠금 순서를 고정했습니다.

```text
users
→ ad_reward_daily_quota
→ ad_reward_session
→ 지급 이력 저장 및 슬롯 증가
```

`transaction_id`에는 전역 UNIQUE 제약을 두고, 이미 처리된 거래는 다시 지급하지 않습니다. 같은 세션에 다른 거래 ID가 들어와도 세션 상태와 세션별 지급 제약으로 추가 지급을 막습니다.

지급 이력 저장, 일일 카운터 증가, 세션을 `GRANTED`로 변경, 사용자 슬롯 증가를 하나의 DB 트랜잭션에서 처리합니다. 중간 단계에서 실패하면 전체 변경을 롤백합니다.

### 검증

다음 테스트로 보상 지급 규칙을 검증했습니다.

- 유효한 서명과 정상 세션이면 슬롯을 지급하고 세션·일일 상태·거래를 함께 확정
- 이미 처리한 `transaction_id`는 다시 지급하지 않음
- 이미 지급된 세션에 다른 거래 ID가 와도 재지급하지 않음
- 광고 단위가 다르면 거절
- `reward_item` 또는 `reward_amount`가 다르면 거절
- 존재하지 않는 `custom_data`는 지급하지 않고 거절 이력만 저장
- 검증 수신 마감이 지난 세션은 만료 처리하고 예약을 반환
- 탈퇴한 사용자에게 지급하지 않음
- 잘못된 서명은 `400`이며 지급 이력을 만들지 않음
- 공개키 조회 실패는 `503`이며 성공 처리하지 않음
- 동일 거래 ID의 동시 콜백도 지급 이력은 하나만 생성되고 슬롯은 한 번만 증가
- 실제 운영 AdMob 서버에서 광고 시청부터 콜백 도착까지의 E2E 검증은 자동화 테스트와 별도 범위임

### 발표용 설명

> “보상형 광고는 앱의 시청 완료 콜백만 믿으면 중복 지급이나 위조가 가능합니다. 그래서 서버가 시청 세션을 먼저 발급하고, Google SSV의 서명과 세션·광고 단위·보상량을 모두 검증한 뒤에만 지급했습니다. 같은 콜백이 재전송돼도 `transaction_id` UNIQUE와 세션 잠금으로 슬롯은 한 번만 증가하고, 거래 이력과 슬롯 변경은 하나의 트랜잭션으로 커밋됩니다.”

### 남은 범위

- 자동화 테스트는 서명 검증, 업무 규칙, DB 동시성을 검증합니다.
- 실제 광고 SDK에서 `custom_data`가 전달되고 운영 AdMob 콜백이 도착하는 과정은 별도 운영 환경 검증이 필요합니다.
- 공개키 캐시 만료나 AdMob 측 재전송 지연은 운영 로그와 메트릭으로 계속 확인해야 합니다.

## 발표에서 두 사례를 연결하는 문장

> “두 기능 모두 외부에서 들어온 값을 그대로 신뢰하지 않고, 서버가 소유한 상태와 DB 제약을 기준으로 최종 결과를 확정했습니다. Refresh Token은 사용자 인증 상태를, AdMob SSV는 보상 지급 상태를 다루지만, 동시 요청·재전송·실패 후 재시도에도 상태가 한 번만 바뀌도록 만든다는 같은 원칙을 적용했습니다.”
