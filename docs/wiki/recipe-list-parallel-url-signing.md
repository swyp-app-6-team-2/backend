# 레시피 목록 조회 지연을 이미지 URL 병렬 서명으로 줄이기

## 요약

- **[문제]** 레시피 목록이 운영 모니터링에서 **가장 느린 API**였고, dev 부하테스트에서도 커버 20장 페이지 기준 **서버 p95 1.1초**로 담당 API 중 가장 느림
- **[해결]** 항목 수별 측정과 스레드 덤프로 이미지 URL 서명(원격 호출)을 **순차로 처리하는 것이 원인**임을 확인하고, **가상 스레드로 동시에 서명**
- **[결과]** 같은 데이터, 거의 같은 요청률로 dev에서 재측정해 **서버 p95 1,107 → 138ms로 개선(8배)**

## 1. 문제 배경

별따먹자는 레시피를 저장하고 모아 보는 앱이다. 레시피 목록 조회(`GET /api/v1/recipes`)는 레시피마다 커버 이미지의 조회 URL(일정 시간만 유효한 Signed URL)을 서명해 응답에 담는다. 이미지는 비공개 버킷에 있어, 앱은 목록 응답을 받아야 사진을 받기 시작할 수 있다.

목록 API를 만들 때(09-09) 서명 1번은 87ms였다. 레시피 수만큼 서명이 순서대로 쌓인다는 점은 당시에도 문제라고 봤지만, 성능 개선은 전체 API 구현 후에 실제 문제로 판단될 때 진행하는 게 맞다고 판단해 [이슈](https://github.com/swyp-app-6-team-2/backend/issues/26)로만 기록해 두고 기능 구현에 먼저 들어갔다.

운영을 시작하자 목록 조회는 매일 아침 받는 운영 보고(prod 지표를 요약해 Discord로 보내는 자동 보고)에서 매번 가장 느린 API로 올라왔다. prod 평균도 206ms로 상세 조회(83ms)의 2.5배였다(09-24 - 10-01). 다만 하루 수십 건뿐인 지표로는 정말 이 API가 병목인지 확신하기 어려웠다. 그래서 목록 조회만 바로 고치지 않고, 담당한 API 전반에 같은 조건으로 부하를 걸어 병목을 먼저 가려낸 뒤 그 결과로 원인을 찾기로 했다.

10-06 dev 서버(e2-medium 1대, vCPU 2개)에서 API 14개에 동시 사용자 10명으로 60초씩 부하를 걸었다(이하 1회차). 사용자마다 커버가 있는 레시피 20개를 넣어, 기본 페이지(20건)가 꽉 차 요청당 서명이 20번 일어나게 했다.


| API                                      | 서버 p95(앱 안에서 잰 처리 시간) |
| ---------------------------------------- | --------------------- |
| `GET /recipes` (목록)                      | **1,107ms**           |
| `GET /recipes?searchQuery` (목록에 검색어를 붙임) | **1,040ms**           |
| 나머지 API 13개                              | 7-74ms                |


결과적으로, 목록과 검색만 나머지보다 14-160배 느렸다. 09-09에 이슈로 남겨 둔 목록 조회가 운영 지표에서 정황으로 드러났고, 부하테스트로 병목임을 확정했다.

## 2. 원인

### 증상

부하를 건 60초 동안 서버 지표의 최댓값을 상세 조회와 비교했다. 동시 사용자 10명이 응답을 받자마자 다음 요청을 보내므로, 두 API 모두 서버 안에는 늘 요청 10개가 있었다. 차이는 그 10개를 처리하는 동안 서버 자원을 얼마나 썼느냐였다.


| API                      | 처리 중인 요청 | VM CPU | DB 커넥션   |
| ------------------------ | -------- | ------ | -------- |
| `GET /recipes/{id}` (상세) | 10       | 92%    | 8        |
| `GET /recipes` (목록)      | 10       | 41%    | 1 (대기 0) |


상세 조회는 CPU를 거의 다 쓰며 일하고 있었지만, 목록 조회는 요청이 들어와 있는데도 CPU는 절반도 쓰지 않았고 DB 커넥션도 거의 빌리지 않았다. 즉, 목록 요청은 CPU나 DB가 아닌 무언가를 기다리고 있다고 예상할 수 있다.

### 확인: 항목 수, SQL, 스레드 덤프

무엇을 기다리는지 가리려고, 코드를 바꾸지 않고 로컬에서 세 가지를 쟀다. 느린 정도가 무엇에 비례하는지, DB 쿼리 때문인지, 요청이 정확히 어디서 멈춰 있는지다.


| 확인하려는 것      | 측정                                             | 결과                                                                      |
| ------------ | ---------------------------------------------- | ----------------------------------------------------------------------- |
| 무엇에 비례해 느려지나 | 커버가 있는 항목과 없는 항목의 수를 바꿔 가며 응답 시간 측정            | 커버가 있으면 1/5/10/20건에 78/320/628/1,231ms로 항목 수에 비례. 커버가 없으면 20건이어도 8-15ms |
| DB 쿼리 때문인가   | 요청당 SQL 수                                      | 항목 수와 관계없이 4개. N+1 없음                                                   |
| 어디서 기다리나     | 로컬에 부하를 걸고 스레드 덤프 10회(각 스레드가 멈춘 코드 위치를 찍은 스냅샷) | 요청 스레드 샘플 100개 중 97개가 IAM 서명 응답을 기다림                                    |


덤프는 아무 순간에나 찍은 스냅샷이라, 97개는 요청 처리 시간의 대부분을 IAM 응답을 기다리는 데 썼다는 뜻이다. 로컬에서 찍은 97개의 스레드는 대부분 아래와 같은 모양이었다(일부 생략). 아래에서 위로 읽으면 목록 조회가 URL을 서명하다가 IAM의 응답을 기다리고 있다.

```text
"http-nio-8080-exec-1" RUNNABLE                         ← 목록 요청을 처리하는 스레드
  at sun.nio.ch.Net.poll                                ← 소켓에서 응답을 기다리는 중
  ...
  at java.net.HttpURLConnection.getResponseCode         ← HTTP 응답 대기
  at com.google.auth.oauth2.IamUtils.getSignature       ← IAM 서명 API 호출
  at com.google.cloud.storage.StorageImpl.signUrl       ← Signed URL 서명
  at ...upload.infrastructure.GcsObjectStorageAdapter.generateViewUrl
  at ...upload.service.UploadService.getViewUrl
  at ...recipe.service.RecipeService.getRecipes         ← 목록 조회
  at ...recipe.controller.RecipeController.getRecipes
```

비용은 커버마다 붙었고, DB 때문이 아니었으며, 그 비용은 IAM 서명 응답을 기다리는 시간이었다. 즉, 항목마다 커버 URL을 서명하고, 서명 1번이 원격 호출 1번이며, 이것을 순서대로 기다리고 있었다. dev에서는 스레드 덤프를 따로 찍지 않았고, 고친 뒤 다시 재는 것으로 확인을 대신했다.

### 서명이 원격 호출인 이유

이미지는 오브젝트 저장소(GCS)에 두고 DB에는 파일 경로인 Key만 저장한다. 앱에 보여 주는 방식은 보통 세 가지다.


| 방식                           | 장점                             | 단점                   |
| ---------------------------- | ------------------------------ | -------------------- |
| 공개 버킷                        | 가장 단순하고 빠르다                    | 주소만 알면 누구나 본다        |
| 서버 프록시                       | 서버가 접근을 완전히 통제한다               | 이미지 바이트가 모두 서버를 지나간다 |
| **비공개 버킷 + Signed URL → 채택** | 접근 통제와 만료가 있고, 앱이 저장소에서 직접 받는다 | URL을 만들 때마다 서명해야 한다  |


사진은 개인 데이터라 Signed URL을 골랐다. Signed URL은 서비스 계정의 개인 키로 서명해야 하고, 키를 어디에 두느냐에 따라 방식이 나뉜다.


| 방식                        | 장점                         | 단점                                           |
| ------------------------- | -------------------------- | -------------------------------------------- |
| 키 파일을 서버에 두고 직접 서명        | 로컬 연산이라 빠르다                | 만료 없는 키가 여러 곳에 퍼지고, 유출되면 폐기 전까지 누구나 서명할 수 있다 |
| **키 없이 IAM에 서명을 맡김 → 채택** | 서버에 키 파일이 없고, 권한을 IAM에서 통제한다 | 서명 1번마다 IAM API 원격 호출이 1번 생긴다                |


Google Cloud 권장대로 키 없이 IAM에 맡겼다. 서명마다 원격 호출이 생기는 대가는 알고 감수한 것이었고, 그 비용이 이미지 수만큼 순서대로 쌓이고 있었다.

## 3. 대안과 선택

지연은 서명 횟수, 서명 1번의 시간, 순서대로 기다림이 곱해진 것이라, 각각을 줄이는 방법을 비교했다.


| 방식               | 장점                                                   | 단점                                                      |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------------- |
| **병렬 서명 → 채택**   | 순서대로 기다리던 시간을 겹친다. API와 DB가 바뀌지 않고 서버에 따로 저장하는 것도 없다 | 원격 호출 횟수는 그대로이고, 한 요청이 서명을 동시에 내보내 연결과 CPU 부담이 늘 수 있다   |
| 서명 URL 캐시 → 보류   | 같은 이미지를 URL 유효시간(60분) 안에 다시 보면 서명이 없다                | 이미지는 본인만 봐 사용자 사이에 재사용되지 않고, 첫 조회는 그대로 느리다 |
| 키 파일로 로컬 서명 → 기각 | 원격 호출 자체가 사라진다                                       | 만료 없는 키를 배포하고 관리해야 한다                                   |


2절에서 확인한 문제는 서명이 원격 호출이라는 점이 아니라, 그 호출을 순서대로 기다린다는 점이었다. 병렬 서명은 바로 그 부분만 고치므로 원인을 가장 정확하게 푼다. 반면 캐시는 효과가 작고, 키 파일은 지연 하나 때문에 보안 결정을 바꾸는 일이다.

## 4. 해결: 병렬 서명

변경 전에는 레시피마다 커버와 원본 대표 이미지(Instagram이나 사진으로 분석해 만든 레시피의 원본 이미지)를 `getViewUrl`로 한 장씩 서명했다. 서명 하나가 끝나야 다음 서명으로 넘어갔다. 아래 코드는 발췌이며 일부를 줄였다.

```java
// 변경 전: RecipeService.getRecipes
recipes.stream()
        .map(recipe -> new RecipeSummary(
                ...
                uploadService.getViewUrl(userId, recipe.getCoverImageKey()),  // 서명 1번 = IAM 호출 1번
                sourceThumbnailUrl(userId, recipe),                         // 원본 대표 이미지도 한 장씩
                ...))
        .toList();
```

변경 후에는 목록의 Key를 모아 업로드 도메인에 한 번에 넘기고, 업로드 도메인이 Key마다 가상 스레드 하나로 동시에 서명한다.

```java
// 변경 후: RecipeService.getRecipes
List<String> keys = ...;                                       // 커버 n개 + 원본 대표 이미지 n개
List<String> urls = uploadService.getViewUrls(userId, keys);   // 한 번에 넘긴다

// 변경 후: UploadService.getViewUrls
public List<String> getViewUrls(Long userId, List<String> objectKeys) {
    List<Future<String>> futures;
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        futures = objectKeys.stream()
                .map(key -> executor.submit(() -> getViewUrl(userId, key)))  // 기존 서명을 Key마다 가상 스레드에서
                .toList();
    }                                                                       // close()가 모든 서명이 끝날 때까지 기다린다
    return futures.stream().map(Future::resultNow).toList();               // 입력 순서대로 돌려준다
}
```

변경 전에는 20장이면 서명 20번을 순서대로 기다렸고, 이제는 동시에 보낸 서명이 모두 끝날 때까지만 기다린다.

### 왜 가상 스레드인가

자바의 일반 스레드는 OS 스레드와 1:1로 묶여, 응답을 기다리는 동안에도 OS 스레드를 붙잡는다. 서명은 대부분 IAM 응답을 기다리는 작업이라, 기다리는 동안 스레드를 어떻게 다루느냐를 기준으로 실행 방식을 골랐다.

| 방식 | 특징 | 이번 경우 |
| --- | --- | --- |
| 고정 크기 스레드 풀 | OS 스레드를 정해진 수만큼 재사용한다. 기다리는 동안에도 스레드를 붙잡는다 | 풀 크기를 정해야 하고, 크기를 넘는 서명은 줄을 선다 |
| 공용 풀(`CompletableFuture` 기본값, `parallelStream`) | 앱 전체가 나눠 쓰며 크기가 CPU 코어 수에 묶인다 | 코어 2개인 dev에서는 20장을 거의 순서대로 처리하고, 앱의 다른 작업까지 밀린다 |
| **가상 스레드 → 채택** | JVM이 관리하는 가벼운 스레드다. 기다리는 순간 OS 스레드에서 내려 두고, 응답이 오면 다시 올려 실행한다 | Key마다 하나씩 만들어도 부담이 적다. 작업마다 새로 만들고 버리는 게 권장 사용법이라 요청마다 실행기를 만든다 |

## 5. 검증

### dev 재측정

1회차와 같은 dev, 같은 데이터로, 요청률도 1회차와 거의 같게(초당 9건) 맞춰 다시 쟀다.

| API | 1회차 p95 | 2회차 p95 | 1회차 평균 | 2회차 평균 |
| --- | --- | --- | --- | --- |
| 목록 | 1,107ms | **138ms (−87.5%)** | 1,044ms | 105ms (−89.9%) |
| 검색 | 1,040ms | **113ms (−89.1%)** | 1,031ms | 102ms (−90.1%) |
| 상세 (변경 없음, 대조군) | 69ms | 59ms | - | - |

목록과 검색 모두 1회차에서 느린 API를 가른 기준(300ms)보다 빨라졌다.

### prod 배포 후

| 기간 | 목록 조회 평균 (요청 수) |
| --- | --- |
| 배포 전 (09-24 - 10-01) | 206ms (246건) |
| 배포 후 첫 보고 (10-06 - 10-07) | 80ms (49건) |
| 배포 후 두 번째 보고 (10-07 - 10-08) | 99ms (47건) |

배포 후 prod 평균은 206ms에서 80-99ms로 낮아졌고, 첫 24시간 서명 실패는 0건이었다. 다만 prod 사용자는 아직 레시피가 적어 요청당 서명이 적으므로, 개선 폭은 dev 결과를 기준으로 본다.

## 6. 한계

아래 두 한계는 지금 규모에서 문제가 된 적이 없어, 서명 실패나 지연 같은 신호가 보일 때 적용한다.

| # | 한계 | 대응 |
| --- | --- | --- |
| 1 | 시간 상한 없음: IAM이 응답하지 않으면 목록 요청이 수 분까지 기다릴 수 있다 | 서명 지연이나 실패가 보이면 목록의 서명 전체에 시간 제한을 두고, 넘긴 장은 URL 없이 응답한다 |
| 2 | 동시 상한 없음: 목록 요청이 동시에 몰리면 IAM으로 나가는 서명과 연결이 크게 늘 수 있다 | 서명 실패나 연결 오류가 보이면 프로세스 전체에 동시 서명 상한을 둔다 |

## 7. 회고

이번 작업에서 가장 잘한 점은 이미 알고 있던 의심도 단계마다 다시 확인한 것이다. 목록 API를 만들며 서명 비용을 위험으로 짚어 이슈로 남겼고, 같은 날 PR 리뷰도 같은 지점을 지적했지만 출시 전 규모라 보류했다. 운영 보고에서 가장 느린 API로 올라왔을 때도 바로 고치지 않고, 맡은 API 전반을 재서 병목부터 확정했다.

원인도 이슈에 적어 둔 서명 지연으로 단정하지 않고 처음부터 다시 확인했고, 그 원인에 맞춰 고친 뒤 같은 데이터, 거의 같은 요청률로 다시 쟀다.
