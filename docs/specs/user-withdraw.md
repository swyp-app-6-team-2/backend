# User Withdrawal Tech Spec

> **문서 버전**: v3 · **기준일**: 2026-09-21
> 이 문서는 API 계약과 회원 탈퇴 처리 정책을 설명하며, v3에는 네이버 연결 해제 구현을 반영한다.

## 1. 확정된 범위

- `DELETE /api/v1/users/me`로 본인 계정을 하드 삭제한다. 네이버 로그인 사용자는 연결 해제를 위해 요청 본문에 `socialAccessToken`을 전달하며, 다른 제공자는 요청 본문을 생략할 수 있다.
- 프로필·레시피·재료·조리 기록·분석 작업·업로드 정보·알림 설정·문의·인증 정보를 삭제한다.
- 광고 거래 이력은 중복 지급 방지를 위해 보존하되 `user_id`, `session_id` 연결을 제거한다. 광고 세션과 일일 카운터는 삭제한다. 따라서 “모든 광고 이력도 삭제한다”는 정책이 아니다.
- 같은 소셜 계정으로 재가입하면 새 user_id를 발급하고 슬롯 10개, 누적 등록 0개, 레시피 0개로 시작한다.
- 최초 탈퇴 요청은 동기로 처리한다. 중간 실패·서버 재시작·토큰 만료에 대비한 **서버 자동 복구 작업을 포함한다.**
- 네이버 로그인 사용자는 로컬 데이터 삭제 전에 네이버 토큰 폐기 API를 호출하여 앱 연결을 해제한다. 토큰 누락 또는 네이버 연결 해제 실패 시 로컬 계정을 삭제하지 않는다. Google·Kakao·Apple 연결 해제는 이번 범위에 포함하지 않는다. 외부 계정 자체를 삭제하는 기능도 아니다.
- 탈퇴 유예, 탈퇴 사유 수집, 완료 알림, 관리자 수동 탈퇴 API, 최초 요청을 무조건 큐에 넣는 비동기 방식은 제외한다.
- 탈퇴 직전 추가 재인증은 도입하지 않는다. 유효한 access token으로 실행한다. 다만 영구 삭제는 로그아웃보다 피해 범위가 크므로, 두 기능의 위험이 같다고 설명하지 않는다.

## 2. 현재 코드와 필요한 변경

| 현재 코드 | 구현 시 필요한 변경 |
|---|---|
| JwtAuthenticationFilter는 JWT 서명·유효기간만 확인 | 인증된 사용자 API에서 사용자 존재 및 deleted_at 확인 추가 |
| 모든 쓰기 경로가 deleted_at을 검사하지는 않음 | 쓰기 트랜잭션 안에서 사용자 잠금 및 활성 상태 재검사 |
| AuthService.revoke()는 lockActiveUser() 호출 | 탈퇴 표시 후 재사용 불가. 시작 트랜잭션에서 Refresh Token을 삭제하는 내부 경계 추가 |
| AuthService.login()은 기존 사용자 토큰 발급 시 issueForActiveUser()를 거침 | 탈퇴 처리 중 계정은 기존 활성 검사로 차단되는 흐름을 유지하고 동시 로그인 검증 |
| RecipeService.deleteRecipe()는 대상 부재 시 404 | 탈퇴용 정리 경로는 이미 삭제된 대상을 건너뛰도록 보완 |
| IngestionJobPurger.purgeOne()는 Job 부재를 허용하지만 일반 조회 사용 | Worker·탈퇴 정리 사이의 잠금과 늦은 결과 처리 보완 |
| UploadService.afterCommit()은 같은 실행 흐름에서 GCS 삭제 | 실패는 탈퇴 성공을 막지 않지만 외부 호출 시간은 응답 지연에 포함됨을 명시 |

기존 deleted_at을 복구 대상 표시로 재사용한다. 도메인 테이블 추가는 기본 설계에 필요하지 않지만, 최신 스키마의 FK 및 복구 조회 인덱스 필요성을 구현 시 검증한다. “마이그레이션은 절대 없다”로 고정하지 않는다.

## 3. 상태와 인증

### 3.1. 상태 정의

| DB 상태 | 의미 | 인증된 일반 사용자 API | 회원 탈퇴 API |
|---|---|---|---|
| users 존재, deleted_at=null | 정상 계정 | 기존 인증 규칙 적용 | 탈퇴 시작 가능 |
| users 존재, deleted_at!=null | 탈퇴 접수 후 정리 중 또는 실패 후 복구 대기 | 401 | 아직 유효한 access token으로 정리 재시도 가능 |
| users 없음 | 삭제 완료 또는 존재하지 않는 사용자 | 401 | 새로 들어온 요청은 401 |

- deleted_at은 탈퇴가 접수되어 정상 서비스 이용이 차단된 시각이다. 삭제 완료 시각이 아니다.
- 최초 표시와 Refresh Token 삭제를 같은 짧은 트랜잭션으로 커밋한다. 실패하면 둘 다 롤백한다.
- 재시도는 기존 deleted_at을 유지한다. 시각을 갱신하여 오래된 복구 대상을 숨기지 않는다.
- JWT의 서명이 유효해도 사용자 행이 없으면 인증된 사용자 API를 이용할 수 없다.
- 정확한 `DELETE /api/v1/users/me`만 탈퇴 처리 중 상태를 허용한다. JWT 서명·만료 검증을 생략하거나 permitAll로 열지 않는다.
- 공개 소셜 로그인, 가입, SSV 콜백 등은 각자의 기존 인증 방식을 유지한다. 모든 공개 요청에 사용자 DB 검사를 강제하지 않는다.
- 탈퇴 중에는 Refresh Token 재발급 및 기존 계정으로 신규 토큰 발급을 허용하지 않는다.

인증 필터의 상태 검사는 새 요청을 차단하는 장치다. 이미 필터를 통과한 요청과 Worker는 별도 트랜잭션 상태 검사가 필요하다.

### 3.2. 응답 계약

| 상황 | 응답 |
|---|---|
| 해당 요청에서 DB 정리 완료를 확인 | 200, `회원 탈퇴가 완료되었습니다.`, data:null |
| 네이버 로그인 사용자의 socialAccessToken 누락 | 400 NAVER_ACCESS_TOKEN_REQUIRED, 로컬 계정 유지 |
| 네이버 토큰 폐기 API 실패 | 502 NAVER_CONNECTION_REVOKE_FAILED, 로컬 계정 유지 |
| 토큰 누락·위조·만료, 요청 진입 시 사용자 없음 | 401 AUTHENTICATION_REQUIRED |
| 탈퇴 처리 중 사용자 + 유효한 access token | 정리를 재시도하고 완료 확인 시 200 |
| DB 정리 중 일시적 실패 | 기존 공통 500 INTERNAL_SERVER_ERROR, 서버 자동 복구 대상 유지 |
| 이미 시작된 두 정리 실행 중 다른 실행이 먼저 완료 | 내부 정리는 성공한 것으로 종료. 처음에 인증·대상 확인을 마친 요청은 200 가능 |

성공 응답은 사용자 행 삭제까지 확인한 뒤 보낸다. 시작 표시만 저장하고 200을 반환하지 않는다. 응답 유실 뒤 새 요청에서 401을 받는 경우와 처리 중 실패를 구분해 프런트에 안내한다.

앱은 성공 시 로컬 토큰을 폐기하고 로그인 화면으로 이동한다. 실패·타임아웃 시 탈퇴가 접수됐을 가능성을 안내하고, 토큰이 아직 유효하면 재시도할 수 있다. 토큰이 만료되어도 서버 복구가 진행되므로 완료를 사용자 재시도에 의존하지 않는다.

### 3.3. 첨부 UI와 프런트 연동

화면 흐름은 `마이페이지 → 로그인 관리 → 회원 탈퇴 → 탈퇴 확인 팝업`이다. 로그인 관리의 로그아웃은 기존 로그아웃 API를 사용하며 회원 탈퇴와 구분한다.

첨부 화면의 확인 문구:
- 제목: `정말 탈퇴하시겠어요?`
- 본문: `탈퇴하면 저장한 모든 레시피와 별 슬롯 기록이 삭제되며 복구할 수 없어요`
- 버튼: `취소`, `탈퇴하기`

| 사용자 동작·결과 | 프런트 동작 | 서버 호출 |
|---|---|---|
| 회원 탈퇴 메뉴 선택 | 확인 팝업 표시 | 없음 |
| 요청 전 취소 선택 | 팝업 닫기, 로그인 관리 화면 유지 | 없음 |
| 탈퇴하기 선택 | 로딩 표시, 중복 터치 방지. 네이버 로그인 사용자는 현재 네이버 access token을 함께 전달 | JWT를 포함한 DELETE /api/v1/users/me. 네이버는 `{ "socialAccessToken": "..." }`, 다른 제공자는 본문 생략 가능 |
| 200 수신 | 로컬 access/refresh token 및 사용자별 캐시 제거, 로그인 화면 이동 | 별도 로그아웃 호출 불필요 |
| 400 NAVER_ACCESS_TOKEN_REQUIRED | 네이버 인증 정보를 다시 확보한 뒤 탈퇴 재시도 | 로컬 계정은 유지됨 |
| 502 NAVER_CONNECTION_REVOKE_FAILED | 잠시 후 재시도 안내 | 로컬 계정은 유지됨 |
| 네트워크 타임아웃 또는 500 | 완료로 단정하지 않고 요청 결과를 확인하지 못했다는 안내 및 재시도 제공 | 토큰이 유효하면 동일 DELETE 재요청 가능 |
| 401 수신 | 로컬 인증 정보 정리 후 로그인 화면 이동. 이 응답만으로 탈퇴 완료를 단정하지 않음 | 만료·잘못된 토큰·삭제 완료를 동일 코드로 구분할 수 없음 |

처리 중·오류 상태는 첨부 UI에 없으므로 위 표는 추가 연동 제안이다. 최초 접수 커밋 뒤에는 팝업 닫기나 앱 종료가 탈퇴 취소를 의미하지 않으며, 서버 자동 복구는 계속 진행한다. 요청을 전송한 뒤에는 `취소`를 탈퇴 철회 버튼처럼 제공하지 않는다.

팝업의 “별 슬롯 기록 삭제”는 사용자에게 연결된 슬롯 한도·이력을 더 이상 복구하거나 승계하지 않는다는 의미다. 중복 지급 방지용 광고 거래 식별자는 사용자 연결을 제거한 채 보존하므로, “광고 거래 식별자까지 모두 삭제”한다고 안내하지 않는다.

## 4. 처리 흐름과 삭제 순서

```text
본인 인증
  → 네이버 계정이면 access token 확인 → 네이버 토큰 폐기 API 호출
  → 시작 트랜잭션: 사용자 잠금 → deleted_at 설정 → Refresh Token 삭제 → 커밋
  → 도메인별 정리(각 단계/작은 배치의 독립 트랜잭션)
  → 최종 트랜잭션: 종속 데이터 확인 → 모든 소셜 연결·프로필·사용자 삭제 → 커밋
  → 200

중간 실패/프로세스 종료
  → users.deleted_at이 남음
  → 자동 복구 작업이 같은 정리 로직 재실행
  → 최종 삭제
```

UserWithdrawalService가 순서를 조율한다. 네이버 연결 해제는 최초 로컬 탈퇴 표시 전에 수행한다. 연결 해제 이후 로컬 정리가 실패하면 deleted_at을 기준으로 자동 복구하며, 복구 작업은 외부 API를 다시 호출하지 않는다. API와 복구 작업은 같은 내부 정리 메서드를 사용한다. 정리 메서드를 외부 API로 추가 노출하지 않는다. 일반 사용자용 메서드의 활성 검사와 구분하여, 내부 정리에서는 탈퇴 표시가 있는 사용자만 처리한다.

| 순서 | 대상 | 처리 |
|---|---|---|
| 0 | users, refresh_tokens | 사용자 잠금 후 deleted_at 최초 설정 및 Refresh Token 삭제. 기존 revoke()를 표시 후 호출하지 않음 |
| 1 | recipe, recipe_ingredient, recipe_step, cook_history | 사용자 레시피를 작은 배치로 조회하고 기존 파일·자식 정리 로직 재사용. 이미 없는 레시피는 건너뜀 |
| 2 | ingestion_job | 레시피 삭제 후 사용자의 **모든 남은 Job** 정리. 소비된 Job도 포함하며 미전환 Job만으로 한정하지 않음 |
| 3 | upload_object | 남은 프로필·문의 첨부·미연결 업로드 등 모든 용도 정리. 커밋 후 파일 삭제 예약 |
| 4 | push_log → push_token → notification_setting | FK 순서에 맞춰 삭제. 이미 발송 중인 외부 푸시의 철회까지 보장하지 않음 |
| 5 | user_ingredient | 해당 사용자 행 삭제 |
| 6 | inquiry | 답변 유무와 무관하게 문의 행 삭제. 첨부는 업로드 정리 단계와 연계 |
| 7 | ad_reward_transaction | user_id 및 해당 사용자 세션 소유 관계로 대상을 찾고 user_id/session_id를 함께 null 처리. transaction_id UNIQUE와 지급/거절 결과 유지 |
| 8 | ad_reward_session, ad_reward_daily_quota | 거래 FK 연결 제거 후 삭제. 사용자 삭제이므로 개별 취소 API를 반복 호출하지 않음 |
| 9 | refresh_tokens | 남은 행이 없음을 보장하는 멱등 정리 |
| 10 | social_credentials, profiles, users | 마지막 한 트랜잭션에서 모든 provider 연결·프로필·사용자 삭제 |

- social_credentials는 최종 단계까지 유지하여 정리가 끝나기 전 같은 소셜 계정으로 신규 가입되는 구간을 줄인다. 탈퇴 중 기존 로그인은 활성 검사에서 거절한다.
- FK 위반 등 최종 삭제 실패 시 마지막 트랜잭션만 롤백된다. 앞서 커밋한 정리 단계까지 복원되는 것은 아니다. deleted_at을 유지해 다음 복구에서 다시 처리한다.
- 광고 거래 이력 보존은 관계 식별자 제거를 의미한다. 로그나 다른 외부 데이터까지 완전한 익명화가 보장된다고 표현하지 않는다. 원문 콜백 로그의 보존·접근 정책도 점검한다.
- 삭제 대상은 고정 테이블 개수로 관리하지 않는다. 최신 마이그레이션과 실제 FK를 기준으로 누락을 확인한다. 추후 커스텀 재료 등 사용자 소유 테이블이 추가되면 정리 대상과 테스트에도 반영한다.
- recipe가 사라져도 남을 수 있는 고아 조리 기록은 현재 스키마의 FK 유무를 확인하고 처리한다. 소유자를 특정할 수 없는 과거 고아 데이터는 이 사용자 탈퇴로 임의 삭제하지 않는다.

## 5. 트랜잭션 및 동시성

### 5.1. 공통 원칙

- 긴 전체 탈퇴 작업을 하나의 DB 트랜잭션이나 하나의 사용자 행 잠금으로 감싸지 않는다.
- 각 정리 단계는 `users → 해당 도메인 행` 순서로 잠그고, 사용자 존재 및 deleted_at을 확인한 뒤 작은 배치만 처리한다.
- 광고는 `users → daily_quota → session` 순서를 유지한다. 거래 관계 제거와 세션 삭제도 같은 사용자 잠금 아래 처리한다.
- 사용자 행이 이미 없으면 내부 정리는 완료로 간주한다. 정상 계정이면 정리를 수행하지 않는다.
- API 재시도와 복구 작업이 겹쳐도 각 단계의 잠금·멱등성이 결과를 보장한다. JVM 내부 락만으로 여러 서버의 중복 실행을 막았다고 가정하지 않는다.
- 탈퇴 표시된 사용자의 일반 쓰기 작업은 사용자 잠금 획득 후 상태를 재검사하고 거절한다. 단순 SELECT 검사 후 나중에 쓰는 방식으로 대체하지 않는다.
- 이미 사용자 잠금을 잡은 쓰기 작업은 먼저 커밋되고, 탈퇴 시작은 그 잠금 해제를 기다린다. 반대로 탈퇴 표시가 먼저 커밋되면 이후 쓰기는 중단한다.
- 현재 분석 Job 선점·소비, 레시피 수정 등은 서로 다른 잠금 순서를 가질 수 있다. `Job/Recipe → users`와 `users → Job/Recipe`가 섞이지 않도록 호출 흐름 전체를 점검한다. 기존 순서를 무조건 안전하다고 가정하지 않는다.
- 프록시를 거치는 별도 트랜잭션 경계 또는 TransactionTemplate을 사용한다. 자기 호출의 @Transactional에 의존하지 않는다.

### 5.2. 검토할 경쟁 경로

| 경로 | 필요한 처리 |
|---|---|
| 레시피 생성·수정·삭제, 조리 기록 작성 | 사용자 잠금과 상태 재검사, 탈퇴 정리와 동일한 잠금 순서 |
| 보유 재료·프로필·알림·문의 변경 | 쓰기 시점 활성 확인. 필터 통과 후 탈퇴가 시작된 요청도 차단 |
| 업로드 URL 발급 | 탈퇴 시작 이후 새 URL·upload_object 발급 차단 |
| 소셜 로그인·회원가입·Refresh Token 발급 | 사용자 상태 및 소셜 연결 UNIQUE 유지, 탈퇴 중 새 토큰/중복 계정 생성 방지 |
| 광고 세션 발급·SSV 콜백 | 사용자 잠금 뒤 탈퇴 상태 확인. 탈퇴 사용자에게 지급하지 않으며, 사용자 삭제 후 콜백도 FK 오류 없이 처리 |
| Ingestion Worker·유지보수 작업 | 탈퇴 사용자 Job 신규 선점 방지, 저장 전 재확인, 이미 사라진 Job 결과는 폐기 |
| 관리자 문의 답변·알림 발송 | 삭제된 문의/수신 대상에 새 DB 행을 쓰지 않도록 재검사 |

외부 분석은 DB 잠금 밖에서 계속 실행될 수 있다. 늦게 완료한 결과가 저장되지 않는 경우 그 작업이 새로 만든 썸네일도 정리하도록 보완한다. 단순 결과 폐기로 파일 삭제까지 끝났다고 간주하지 않는다.

## 6. 자동 복구 작업 — 이번 구현에 포함

### 6.1. 대상 및 실행

- 대상은 `users.deleted_at IS NOT NULL`인 사용자다. API 실패 여부를 별도 메모리에만 저장하지 않는다.
- 내부 스케줄러가 소규모 배치로 대상 ID를 읽고, API와 동일한 도메인 정리를 실행한다. JWT가 없어도 동작하는 내부 작업이며 외부 무인증 API가 아니다.
- 제안 초기 설정: `fixedDelay=60초`, 회차당 `batchSize=20`. 설정으로 조정하며 확정된 제품 정책으로 간주하지 않는다.
- 한 사용자 실패가 다음 사용자를 막지 않도록 사용자별 예외를 격리한다. 단계 실패 시 해당 사용자 실행을 멈추고 다음 대상 처리로 넘어간다.
- 정상 처리 중인 API와 겹칠 수 있으므로 5장의 잠금·멱등 규칙을 그대로 적용한다. 긴 외부 호출 동안 사용자 락을 유지하지 않는다.
- 대상 조회는 안정적인 user_id 키셋 순회와 다음 회차 커서를 사용한다. 매번 첫 20명만 재시도하여 영구 실패 계정이 뒤의 계정을 막지 않도록 한다. 끝에 도달하면 다시 처음부터 순회한다.
- 프로세스 재시작 시 커서가 초기화되어도 deleted_at 대상은 남으므로 재처리할 수 있다. 반복 실패는 다음 순회에서 다시 시도하며 hot loop로 즉시 무한 재시도하지 않는다.
- 모든 서버가 실행해도 정합성을 보장한다. 효율 개선을 위한 전역 스케줄러 리더/lease는 필요 시 추가하되 완료 보장을 JVM 단독 상태에 의존하지 않는다.

### 6.2. 완료 및 운영 확인

- 사용자 행이 삭제되면 다음 대상 조회에서 자연스럽게 제외된다.
- 실패해도 deleted_at을 null로 되돌리지 않는다. 부분 삭제된 계정을 정상 상태로 복구하지 않는다.
- 시작 시각 대비 오래 남은 대상 수, 가장 오래된 지연 시간, 단계별 실패와 성공 건수를 관측한다.
- 제안 알림 기준은 탈퇴 접수 후 1시간 이상 잔존하거나 반복 실패가 발생한 경우다. 운영 환경에 맞춰 조정한다.
- 자동 복구의 완료 범위는 DB 정리다. 이미 DB 키를 잃은 GCS 파일까지 재시도할 수 있다고 주장하지 않는다(7장).

## 7. GCS 및 외부 시스템 경계

- DB 삭제 성공 후 파일 삭제가 실패해도 회원 탈퇴의 DB 정리를 계속한다.
- afterCommit은 비동기 작업 큐가 아니다. 현재 코드에서는 GCS 호출 시간이 응답 시간에 포함된다. 저장소 타임아웃과 배치 크기를 점검한다.
- 기존 코드와 동일하게 파일 삭제는 커밋 이후 수행한다. DB 롤백 전에 파일을 먼저 지우지 않는다.
- DB 커밋과 afterCommit 실행 사이에 프로세스가 종료되거나 파일 삭제가 실패하면 파일이 남을 수 있다. 완전한 재시도가 필요하면 파일 삭제용 내구성 있는 작업 기록/outbox를 별도 설계해야 한다. 이번 DB 복구 작업만으로 해결되는 문제는 아니다.
- 이미 발급된 GCS 서명 URL은 사용자 DB 삭제만으로 즉시 무효화되지 않는다. 탈퇴 전에 발급된 URL로 뒤늦게 업로드된 파일이 남을 수 있다는 한계를 문서화한다.
- Worker가 탈퇴 후 생성한 파일은 저장 실패 경로에서 명시적으로 정리한다. 삭제 실패 시 기존 저장소 오류 정책과 운영 관측을 따른다.
- 문의를 DB에서 삭제해도 이미 전송한 Discord 메시지나 외부 분석 서비스 기록까지 삭제되는 것은 아니다. 외부 데이터 삭제는 이 API의 완료 보장에 포함하지 않는다.
- 네이버 연결은 로컬 삭제 전에 해제한다. Google·Kakao·Apple은 이번 범위에서 제공자 연결을 해제하지 않으므로 해당 제공자의 계정 화면에는 앱 연결이 남을 수 있다.

## 8. 재가입

- 최종 트랜잭션에서 social_credentials와 users를 삭제한 뒤 기존 소셜 로그인은 가입용 토큰 발급 흐름으로 진입한다.
- 탈퇴 정리 중에는 소셜 연결이 남아 있어 기존 계정으로 조회되지만 issueForActiveUser()의 활성 검사에서 거절한다.
- 이전에 발급된 SignupToken으로 진행하는 요청도 기존 소셜 연결 존재 여부와 UNIQUE 제약을 따라야 한다. 동시 탈퇴/가입을 테스트한다.
- 재가입 시 새 user_id, 기본 프로필, 슬롯 10개, 누적 등록 0개, 온보딩 필요 상태를 확인한다.
- 이전 사용자 토큰으로 새 계정에 접근할 수 없어야 한다. 익명화된 광고 거래의 동일 transaction_id 재수신도 새 계정에 보상하지 않는다.

## 9. 로깅과 테스트

로그는 userId, 단계 이름, 소요 시간, 성공/실패 분류 위주로 남긴다. 토큰, 이메일, 닉네임, 문의 내용, 원문 소셜 응답은 남기지 않는다. 보존 로그의 userId가 있으므로 광고 FK 제거만으로 모든 추적 정보까지 사라진다고 설명하지 않는다.

## 10. 구현 전 추가 결정 여부

현재 확정된 MVP 범위에서 구현을 막는 추가 사용자 결정은 없다. 복구 주기·배치 크기·알림 기준은 위 제안값으로 설정화할 수 있다.

프런트에는 네이버 사용자의 `socialAccessToken` 전달 계약과 400/502 처리, 탈퇴 실패/타임아웃/401 안내, 처리 중 재로그인 제한을 공유한다. `inquiry.md`의 탈퇴 회원 문의 보존 설명은 기능 구현 시 본 문서와 맞춘다. GCS 파일의 영구 삭제까지 보장하는 내구성 있는 정리 기능은 별도 범위로 관리한다.
