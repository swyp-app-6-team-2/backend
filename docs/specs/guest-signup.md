# 게스트의 신규 회원가입과 기존 데이터 정리

관련 이슈: #134

## 1. 정책 및 범위

- 게스트에서 신규 회원가입하면 별도 `MEMBER` 계정을 생성한다. 게스트의 레시피·재료·프로필·별·온보딩 기록을 이전하거나 합치지 않는다.
- 새 회원은 별 슬롯 10개, 누적 레시피 등록 0개, 기본 프로필, 온보딩 필요 상태로 시작한다.
- 가입이 확정되기 전 오류가 발생하면 게스트와 기존 기록을 유지한다.
- 신규 가입 성공 시 기존 게스트는 즉시 정리 대상으로 전환한다. 이후 일반 API 접근과 refresh token 갱신을 차단한다.
- 이미 가입된 소셜 계정으로 로그인하는 흐름은 이번 변경에 포함하지 않는다. 소셜 로그인만으로 게스트를 정리하지 않는다.
- 앱 삭제 감지, 미사용 게스트의 자동 만료, 게스트 데이터 승계는 구현하지 않는다.
- 프론트 수정은 별도 작업이다. 서버 토큰 없이 로컬에만 저장한 게스트 데이터는 서버에서 식별하거나 삭제할 수 없다.

## 2. API 명세

기존 `POST /api/v1/auth/signup`을 확장한다. 신규 엔드포인트는 추가하지 않는다.

### 요청 헤더

| 헤더 | 내용 |
|---|---|
| `Content-Type` | `application/json` |
| `Authorization` | 일반 가입은 생략. 게스트 전환 가입은 `Bearer {게스트 accessToken}` 필수 |

헤더 생략과 잘못된 헤더를 구별한다. 헤더를 전달했는데 인증에 실패하면 일반 가입으로 대체하지 않는다.
토큰의 서명·종류·만료·사용자 존재·활성 상태·GUEST 타입을 검증한다.
정리 대상 ID는 검증한 토큰에서만 얻으며 본문의 `userId`/`guestUserId`는 사용하지 않는다.

### 요청 본문 — 기존 형식 유지

```json
{
  "signupToken": "소셜 로그인에서 받은 가입용 토큰",
  "ageOver14Agreed": true,
  "serviceTermsAgreed": true,
  "privacyAgreed": true,
  "marketingAgreed": false,
  "serviceAgreed": false
}
```

앞의 세 동의는 true 필수, 뒤의 두 동의는 값 전달이 필수이며 false도 허용한다.
`signupToken`과 헤더의 게스트 `accessToken`은 용도가 다르다.

### 성공 — 200

```json
{
  "status": 200,
  "message": "회원가입이 완료되었습니다.",
  "data": {
    "userId": 123,
    "accessToken": "새 회원의 accessToken",
    "refreshToken": "새 회원의 refreshToken",
    "onboardingRequired": true
  }
}
```

200은 새 회원 생성과 게스트 접근 차단이 커밋되었다는 의미다. 기존 데이터의 물리적 삭제 완료를 기다리지 않는다.

### 실패

| HTTP | 구분 | 동작 |
|---|---|---|
| 400 | 기존 필수 동의/요청 검증 오류 | 가입·게스트 전환 없음 |
| 401 | 기존 가입용 토큰 오류 | 가입·게스트 전환 없음 |
| 401 | `GUEST_TOKEN_INVALID` | 잘못된 인증 헤더, 만료·위조·다른 종류의 게스트 토큰, 계정 없음 또는 이미 정리 대상 |
| 403 | `GUEST_ACCOUNT_REQUIRED` | 게스트 대신 정식 회원의 accessToken을 전달함 |
| 409 | 기존 소셜 계정 중복 가입 오류 | 새 회원을 만들지 않고 기존 게스트 유지 |
| 500 | `INTERNAL_SERVER_ERROR` | 가입 트랜잭션 실패 시 회원 생성·게스트 전환·토큰 폐기 모두 롤백 |

신규 게스트 오류 코드는 공통 오류 응답의 `data.code`에 담는다. 기존 `SignupException` 응답 형식은 변경하지 않는다.
이미 정리 대상이었던 게스트의 401 응답이 그 게스트를 복구하거나 정리를 취소하지는 않는다.

## 3. 트랜잭션과 동시성

```text
가입 토큰/필수 동의/게스트 인증 헤더 검증
  → DB 트랜잭션 시작
  → 게스트 사용자 행 잠금, 활성 상태와 계정 타입 확인, 토큰 만료 재검증
  → 별도의 새 회원·프로필·소셜 연결·인증 토큰 저장
  → 기존 게스트 deleted_at 표시 및 refresh token 삭제
  → 함께 커밋
  → 새 회원 응답
```

- 기존 `UserLifecycleGuard`의 DB 행 잠금을 사용한다. JVM 내 락에 의존하지 않는다.
- 같은 게스트로 서로 다른 소셜 가입을 동시에 요청해도 첫 커밋 이후 요청은 활성 상태 재검사에서 401로 거절한다.
- 서로 다른 게스트가 같은 소셜 계정으로 가입하면 기존 `uk_provider_social_uid` UNIQUE 제약이 중복 회원 생성을 막는다. 실패한 트랜잭션의 게스트는 유지한다.
- 게스트 사용자 쓰기 및 토큰 갱신과도 기존 사용자 행 잠금 규칙을 공유한다.
- 성공 응답 유실 후 같은 게스트로 요청하면 401이 될 수 있다. 헤더를 제거하고 가입을 자동 재시도하지 말고, 해당 소셜 계정으로 다시 로그인하여 이미 만들어진 회원을 사용한다.

## 4. 데이터 정리 및 복구

기존 `UserWithdrawalRecovery` → `UserWithdrawalService.resume()`를 재사용한다.
정리 대상은 `users.deleted_at IS NOT NULL`로 DB에 남기며 메모리 이벤트나 AFTER_COMMIT 리스너에 실행 보장을 의존하지 않는다.

- 기본 설정은 60초 간격, 회차당 20명이다. 실제 정리 시점은 대기 대상 수와 실패 여부에 따라 달라진다.
- 레시피·요리 기록·분석 작업·업로드·알림·재료·문의·프로필 등을 기존 탈퇴 순서로 정리한다.
- 광고 거래 식별자는 중복 지급 방지를 위해 유지하고 사용자·세션 연결을 제거한다.
- 일부 단계만 성공해도 기존 게스트는 비활성 상태를 유지한다. 새 회원은 정리 실패와 무관하게 유지된다.
- 다음 순회에서 실패 대상을 재시도한다. 프로세스 재시작으로 커서를 잃어도 DB 표시를 다시 조회한다.
- 반복 실패한 대상은 남겨두고 로그를 기록하며, 다른 대상도 계속 처리한다. 1시간 이상 지연된 대상은 기존 경고 로그로 확인한다.
- 이미 삭제된 대상을 다시 실행해도 안전하다. 활성 게스트는 자동 정리 대상이 아니다.
- `user-withdrawal.recovery.enabled`가 활성화되어 있어야 자동 정리가 실행된다. 기존 운영 기본값은 true이며 새 환경변수나 마이그레이션은 추가하지 않는다.

일반 API와 토큰 갱신은 차단하지만, 기존 탈퇴 계약에 따라 유효한 accessToken을 사용하는 `DELETE /api/v1/users/me`는 정리 재시도에 사용할 수 있다.

### 외부 이미지 삭제의 기존 한계

이 복구 보장은 DB 정리에 해당한다. 기존 GCS 파일 삭제는 커밋 이후 best-effort 방식이다.
DB 커밋 직후 프로세스 종료 또는 GCS 오류로 파일이 남으면 이 작업만으로 영구적인 재삭제를 보장하지 않는다.
내구성 있는 파일 삭제 큐/outbox는 별도 작업이다. 상세 경계는 `user-withdraw.md` 7장을 따른다.

## 5. 프론트 전달 사항

1. 서버 `POST /api/v1/auth/guest`로 발급받은 게스트 토큰을 신규 가입 완료 전까지 유지한다.
2. 소셜 로그인으로 `signupToken`을 받으면 약관 동의 후 `/signup`에 본문과 게스트 Authorization 헤더를 함께 전달한다.
3. 200 수신 후 새 회원 토큰으로 교체하고 기존 게스트의 로컬 데이터·사용자별 캐시를 제거한다. 온보딩은 새로 시작한다.
4. 가입 실패 시 게스트 기록을 먼저 지우지 않는다. 게스트 accessToken 만료는 유효한 refreshToken으로 갱신한 뒤 재시도한다.
5. 회원 로그아웃 후 게스트 이용을 다시 선택하면 새 게스트를 생성한다. 이전 게스트 토큰/기록을 복원하지 않는다.
6. 기존 회원으로 소셜 로그인한 경우는 신규 가입 전환과 구별한다. 기존 회원과 게스트 기록을 합치지 않는다.

## 6. 검증

`GuestSignupApiTest`에서 HTTP 계약, 새 회원 기본값, 다른 사용자 보존, 게스트 인증 차단,
위조된 본문 ID 무시, 가입/토큰 폐기 실패 롤백, 두 종류의 동시 가입,
정리 실패 후 새 복구 인스턴스의 재개 및 Swagger 선택적 인증 명세를 검증한다.
전체 데이터 정리 및 다중 복구 실행의 멱등성은 기존 `UserWithdrawalApiTest`도 함께 검증한다.
