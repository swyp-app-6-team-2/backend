# Upload Tech Spec

> **문서 버전**: v1 · **기준일**: 2026-09-07
>
> `recipe.md`와 `cooking.md`가 "Image Upload Common Spec"이라는 이름으로 링크하는 문서가 이 문서다.

## 한눈에 보기

Upload는 이미지 파일 자체를 다루지 않는다. 사용자가 클라우드 저장소에 **직접** 올릴 수 있는 임시 접근 권한을 발급하고, 발급한 객체가 어느 리소스에 쓰였는지만 추적한다.

| 질문                   | 답변                                                                             |
|----------------------|--------------------------------------------------------------------------------|
| 무엇을 관리하는가?           | UploadObject. 서버가 발급한 저장소 객체 이름(`objectKey`)의 소유자·용도·연결 여부                     |
| 사용자는 무엇을 할 수 있는가?    | 업로드용 임시 URL을 발급받아 클라우드 저장소에 직접 업로드                                             |
| 어떤 API를 제공하는가?       | 업로드 URL 발급 1개                                                                  |
| 핵심 데이터는 무엇인가?        | UploadObject                                                                   |
| 어떤 도메인과 협력하는가?       | [Recipe](./recipe.md)·[Cooking](./cooking.md)·Ingestion에 연결·조회·정리 수단을 제공       |
| 핵심 기술 결정은 무엇인가?      | 조건부 UPDATE 한 번으로 `objectKey`를 평생 한 리소스에만 연결하고, 서명은 서비스 계정 키 파일 없이 클라우드 IAM에 위임 |
| MVP에서 제외하거나 감수하는 것은? | 버려진 객체의 자동 정리를 두지 않고, URL에 서명할 때마다 원격 호출 1회를 감수함                               |

## 1. 개요

### 1.1. 왜 서버가 이미지를 받지 않는가

가장 단순한 방법은 클라이언트가 이미지를 API 서버로 보내고 서버가 저장소에 올리는 것이다. 이 방식은 쓰지 않기로 했다.

이미지 한 장이 수 MB이고 사용자가 레시피를 저장할 때마다 올린다. 서버가 중계하면 그 트래픽과 메모리를 API 서버가 그대로 떠안고, 업로드가 느린 회선에서는 요청 스레드가 오래 잡힌다. 이미지 전송량이 늘수록 비즈니스 로직 처리 능력이 함께 줄어드는 구조가 된다.

그래서 **바이너리는 클라이언트와 클라우드 저장소가 직접 주고받고, 서버는 "누가 무엇을 올릴 수 있는지"만 통제한다.
** 서버는 임시 접근 권한이 담긴 URL을 발급하고, 그 URL로 올라온 객체가 실제로 어느 레시피의 사진이 되는지를 관리한다.

대신 서버가 업로드 순간을 직접 보지 못한다는 대가가 생긴다. 이 문서의 상당 부분이 그 대가를 다루는 규칙이다.

### 1.2. 전체 흐름

```text
1. Client ── "RECIPE_COVER 용도로 jpeg 올릴게" ──▶ Upload
2. Client ◀── objectKey + 업로드 URL + 함께 보낼 헤더 + 만료시각 ── Upload
3. Client ── 이미지 바이너리 ──▶ 클라우드 저장소 (서버를 거치지 않음)
4. Client ── objectKey ──▶ Recipe (레시피 생성/수정 요청에 포함)
5.                          Recipe ── "이 objectKey 써도 되나" ──▶ Upload
6.                          Recipe ◀── 연결 성공 / 유효하지 않음 / 이미 쓰임 ── Upload
```

### 1.3. 용어

| 용어             | 뜻                                                                                        |
|----------------|------------------------------------------------------------------------------------------|
| GCS            | Google Cloud Storage. 이 서비스가 쓰는 클라우드 파일 저장소                                              |
| `objectKey`    | 저장소 안에서 파일 하나를 가리키는 이름. 예: `recipe-covers/1/a3f2....jpg`. DB에는 URL이 아니라 이 값을 저장한다        |
| Signed URL     | 특정 파일에 대해 정해진 시간·방식으로만 접근을 허용하는 서명된 임시 URL. 이 URL을 가진 사람은 별도 로그인 없이 그 동작만 할 수 있다         |
| V4             | GCS Signed URL의 서명 방식 버전. 현재 권장 방식이며 서명에 포함할 헤더를 지정할 수 있다                                |
| IAM            | 클라우드의 권한 관리 체계. 이 문서에서는 "서명을 대신 수행해주는 클라우드 기능"이라는 뜻으로 쓴다                                 |
| 서비스 계정         | 사람이 아니라 애플리케이션에 부여하는 클라우드 계정                                                             |
| **소비 도메인**     | 발급된 `objectKey`를 실제로 자기 데이터에 붙여 쓰는 도메인. Recipe(대표 이미지), Cooking(완성 사진), Ingestion(분석 입력) |
| Ingestion      | URL이나 이미지를 분석해 레시피 초안을 만드는 도메인. 분석 입력 이미지를 이 계약으로 올린다                                    |
| 공통 응답 Envelope | 모든 API가 `status` / `message` / `data` 세 필드로 감싸 응답하는 이 서비스의 공통 형식                         |
| 버려진 객체         | 업로드는 됐지만 어떤 리소스에도 연결되지 않은 채 남은 저장소 파일                                                    |

## 2. 목표와 범위

### 2.1. 목표

- 용도별 업로드 URL 발급과 `objectKey` 생성
- 발급한 `objectKey`의 소유자·용도·연결 여부 추적
- 하나의 `objectKey`가 두 리소스에 연결되지 않도록 보장
- 조회용 URL 발급과 저장소 파일 삭제를 소비 도메인에 제공

### 2.2. MVP 제외 범위

- 버려진 객체의 자동 탐지·삭제. 업로드해놓고 저장을 취소하면 파일이 남는데, 이 비용을 감수한다
- CDN, 이어올리기(Resumable Upload)
- 업로드 URL 재발급·연장. 만료되면 새로 발급받는다
- **업로드 파일 크기 제한.** Signed PUT URL은 구조적으로 크기 조건을 걸 수 없고(크기 조건은 POST 정책 전용), 연결 시점의 존재 확인도 크기를 보지 않는다. 따라서 인증된 사용자가 임의 크기의 파일을 올려 연결할 수 있다.

  감수하는 이유는 업로드가 서버를 거치지 않기 때문이다. 큰 파일이 올라와도 API 서버의 자원을 쓰지 않으므로 가용성 문제가 아니라 저장소 비용 문제이고, 비용은 청구서로 관찰된다. 필요해지면 존재 확인이 이미 받아오는 객체 정보에서 크기를 함께 보면 되므로 추가 원격 호출 없이 나중에 넣을 수 있다.

  **전환 트리거**: 저장소 사용량이 예상 밖으로 늘면 상한을 도입한다. 상한 값은 제품 결정이다.

### 2.3. 도메인 협력

```text
Recipe / Cooking / Ingestion ── 연결·해제·조회 URL 요청 ──▶ Upload
Upload ── URL 서명, 파일 존재 확인, 파일 삭제 ──▶ GCS
```

Upload는 소비 도메인의 Repository나 Entity를 알지 못한다. 호출은 항상 소비 도메인에서 Upload로만 향한다.

## 3. 기술 설계

### 3.1. 주요 처리 흐름

#### 발급

1. 사용자가 용도(`purpose`)와 형식(`contentType`)을 전달한다.
2. 서버가 `objectKey`를 만들고 UploadObject를 **미연결 상태**로 저장한다.
3. 서버가 업로드용 Signed URL을 발급해 `objectKey`와 함께 반환한다.

#### 업로드

사용자가 발급받은 URL로 저장소에 직접 올린다. 이때 응답으로 받은 `uploadHeaders`를 **그대로
** 함께 보내야 한다. 이 헤더들이 서명에 포함되어 있어서, 하나라도 빠지거나 값이 다르면 저장소가 거부한다(빠뜨리면 `400 MalformedSecurityHeader`).

#### 연결

소비 도메인이 `objectKey`를 받아 Upload에 연결을 요청한다. 다음을 모두 만족해야 성공한다.

- UploadObject가 존재한다
- 요청자가 발급받은 본인이다
- 용도가 일치한다
- 아직 어디에도 연결되지 않았다
- 저장소에 파일이 실제로 존재한다 (사용자가 발급만 받고 올리지 않았을 수 있다)

Upload는 **결과를 세 가지로만 구분해 돌려준다** — `연결 성공`, `유효하지 않음`,
`이미 연결됨`. HTTP 상태와 공개 오류 코드는 소비 도메인이 정한다. 같은 실패라도 Recipe에서는 대표 이미지 오류이고 Cooking에서는 사진 오류이기 때문이다.

#### 같은 `objectKey`를 다시 보낸 경우

수정 API에서 이미지를 그대로 두고 다른 필드만 고칠 때, 클라이언트가 화면의 값을 통째로 보내면서 이미 연결된 `objectKey`를 다시 실어 보낼 수 있다.

이 경우 **소비 도메인이 연결을 요청하기 전에 걸러낸다.** 저장된 값과 같은
`objectKey`면 이미지 관련 작업을 아예 하지 않는다. Upload에 그대로 넘기면 "이미 연결됨"으로 판정되어 정상적인 수정이 실패하기 때문이다.

#### 조회

소비 도메인이 저장된 `objectKey`로 조회용 Signed URL을 요청해 응답에 담는다. 서버는 이미지 바이너리를 중계하지 않는다.

조회 URL의 유효시간은 **60분**이다. 업로드 URL(15분)보다 긴 이유는 사용자가 상세 화면을 열어둔 채 한참 뒤에 스크롤해도 이미지가 깨지지 않아야 하기 때문이다.

서명에 실패하면(클라우드 일시 장애 등) 조회 URL을 `null`로 응답한다. 이미지 한 장 때문에 레시피 조회 전체를 실패시키지 않는다.

요청자가 `objectKey`의 발급 대상이 아니어도 같은 `null`을 응답한다. 판단 방식은 §3.4 `해제와 삭제`에 있다.

#### 정리

소비 도메인이 이미지 참조를 **제거**할 때 UploadObject도 같은 트랜잭션에서 제거한다. 저장소 파일 삭제는 커밋 이후 한 번만 시도하며, 실패해도 이미 완료된 DB 변경과 성공 응답을 유지한다.

서버는 삭제한 `objectKey`를 다시 발급하지 않는다. `objectKey`에 임의로 생성한 식별자(UUID)가 들어가 사실상 재사용되지 않으며, UploadObject가 없는
`objectKey`는 연결이 거부되므로 과거 값을 다른 리소스에 붙일 수 없다.

#### 예외: 소유 도메인이 바뀌는 경우

Ingestion이 분석에 쓴 입력 이미지가 최종 Recipe의 원본 이미지로 넘어갈 때는 **UploadObject를 지우지 않는다.
** 참조가 사라지는 것이 아니라 소유 도메인만 Ingestion에서 Recipe로 바뀌는 것이기 때문이다. 이때 UploadObject는 연결된 상태 그대로 유지된다.

### 3.2. 데이터 모델

#### UploadObject

| 속성           | 필수 | 규칙                                                      |
|--------------|----|---------------------------------------------------------|
| `objectKey`  | O  | 식별자. 서버가 생성하며 삭제한 값을 다시 발급하지 않는다                        |
| `userId`     | O  | 발급받은 사용자. 다른 도메인 Entity를 참조하지 않는 스칼라 값                  |
| `purpose`    | O  | `RECIPE_COVER`, `COOK_HISTORY_PHOTO`, `INGESTION_INPUT` |
| `attachedAt` | X  | 연결 시각. 값이 없으면 미연결이며, 연결 이후 다시 비우지 않는다                   |

`objectKey`는 `{용도별 prefix}/{userId}/{임의 식별자}.{확장자}` 형태다. 예: `recipe-covers/1/a3f2e8b1-....jpg`

| 용도                   | prefix             | 
|----------------------|--------------------|
| `RECIPE_COVER`       | `recipe-covers`    |
| `COOK_HISTORY_PHOTO` | `cook-history`     |
| `INGESTION_INPUT`    | `ingestion-inputs` |

확장자는 형식에서 정한다. `image/jpeg` → `jpg`, `image/png` → `png`, `image/webp` → `webp`.

### 3.3. API 설계

| Method | Endpoint                 | 기능         |
|--------|--------------------------|------------|
| `POST` | `/api/v1/uploads/images` | 업로드 URL 발급 |

인증된 사용자만 호출할 수 있다.

#### 요청

| 속성            | 필수 | 규칙                                                      |
|---------------|----|---------------------------------------------------------|
| `purpose`     | O  | `RECIPE_COVER`, `COOK_HISTORY_PHOTO`, `INGESTION_INPUT` |
| `contentType` | O  | `image/jpeg`, `image/png`, `image/webp`                 |

#### 응답

성공은 `200 OK`다. 이 API가 만드는 것은 클라이언트가 받아 가는 리소스가 아니라 **접근 권한**이고, UploadObject 저장은 내부 부수효과이기 때문이다.

| 속성              | 규칙                                                                   |
|-----------------|----------------------------------------------------------------------|
| `objectKey`     | 이후 비즈니스 API에 전달할 안정적인 식별자                                            |
| `uploadUrl`     | 업로드용 Signed URL                                                      |
| `uploadHeaders` | 업로드 요청에 그대로 포함해야 하는 헤더. `Content-Type`과 `x-goog-if-generation-match` |
| `expiresAt`     | 만료 시각. 발급 시점부터 15분. ISO 8601 UTC(`...Z`)                             |

`x-goog-if-generation-match: 0`은 "대상 위치에 파일이 없을 때만 허용"이라는 조건이다. 이미 있으면 저장소가 `412 Precondition Failed`로 거부해 덮어쓰기를 막는다.

저장소로 직접 보내는 업로드 요청의 응답은 이 서비스의 공통 응답 Envelope 대상이 아니다.

#### 실패 응답

| 상황                             | 응답                                |
|--------------------------------|-----------------------------------|
| `purpose` 또는 `contentType` 미전달 | `400 + REQUEST_VALIDATION_FAILED` |
| `contentType`이 지원 형식이 아님       | `400 + REQUEST_VALIDATION_FAILED` |
| `purpose`가 정의된 값이 아님           | `400 + INVALID_REQUEST_FORMAT`    |
| 인증 실패                          | `401 + AUTHENTICATION_REQUIRED`   |

이 API는 전용 오류 코드를 두지 않는다. 실패가 요청 형식 문제뿐이라 공통 코드로 충분하다. 같은 400이 두 코드로 나뉘는 이유는, 값이 잘못된 것(
`REQUEST_VALIDATION_FAILED`)과 요청 본문을 해석조차 못 한 것(`INVALID_REQUEST_FORMAT`)을 이 서비스가 구분하기 때문이다. 정의되지 않은
`purpose` 문자열은 후자로 처리된다.

### 3.4. 트랜잭션과 원격 호출 경계

Upload의 작업은 DB 변경과 클라우드 원격 호출이 섞여 있다. **서비스 계정 키 파일을 두지 않고 IAM에 서명을 위임하므로, URL 서명 자체가 원격 호출이다.** 이 점이 트랜잭션 경계 판단의 전제다.

| 작업        | DB         | 원격 호출       |
|-----------|------------|-------------|
| 발급        | INSERT     | 서명 1회       |
| 연결        | 조건부 UPDATE | 파일 존재 확인 1회 |
| 조회 URL 발급 | 없음         | 서명 1회       |
| 해제        | DELETE     | 없음          |
| 파일 삭제     | 없음         | 삭제 1회<sup>*</sup> |

<sup>*</sup> Key가 여러 개여도 한 번이다. 저장소가 지원하는 batch 삭제를 쓴다. 이유는 아래 `해제와 삭제`에 있다.

세 경로는 위험도가 다르므로 같은 방침으로 묶지 않는다.

| 경로 | 트랜잭션이 쥐는 것                         | 원격 호출 위치                 |
|----|------------------------------------|--------------------------|
| 발급 | 없음. 저장 한 번이라 별도 경계를 두지 않는다          | **트랜잭션 밖**               |
| 조회 | Upload는 트랜잭션을 열지 않는다. Recipe 상세 조회는 소비 도메인의 읽기 트랜잭션 안에서 부르고, Cooking 이력 조회는 트랜잭션 밖에서 부른다([Cooking Spec](./cooking.md) §3.4). 쓰기 잠금은 없다 | Recipe: 소비 도메인 트랜잭션 안 / Cooking: 트랜잭션 밖 |
| 연결 | 소비 도메인의 트랜잭션에 참여. 수정 시 대상 레시피 행의 잠금 | 트랜잭션 안, **타임아웃으로 상한을 검** |

연결 경로가 유일하게 주의가 필요하다. 잠금을 쥔 채 원격 호출을 하기 때문인데, 위험한 것은 평상시 지연(수십 ms)이 아니라 네트워크 장애 시의 꼬리 지연이다. 저장소 클라이언트에 연결 2초·읽기 3초, 최대 시도 2회, 전체 5초를 명시해 최악의 잠금 보유 시간을 **약 5초**로 제한한다.

**상한이 적용되는 범위에 주의한다.** 저장소 클라이언트에 건 타임아웃은 파일 존재 확인·삭제 같은 저장소 API 호출에만 적용된다. **URL 서명은 이 설정의 보호를 받지 않는다** — 서명은 저장소 API가 아니라 자격증명 객체에 위임되고, 키 파일이 없는 구성에서는 인증 라이브러리가 자기 설정으로 IAM을 호출하기 때문이다.

그래도 설계가 성립하는 이유는, 상한이 가장 절실한 경로가 존재 확인이기 때문이다. 이것만 잠금을 쥔 채 일어난다. 서명은 발급(트랜잭션 밖)과 조회(읽기 트랜잭션, 쓰기 잠금 없음)에서만 쓰이고, 조회는 실패해도 URL을 `null`로 낮춰 응답을 살린다.

##### 알려진 한계 — 조회가 DB 커넥션을 쥔 채 서명한다

조회에는 쓰기 잠금이 없지만 **DB 커넥션은 쥐고 있다.** 소비 도메인의 읽기 트랜잭션 안에서 불리기 때문이다. 이 한계는 **Recipe 상세 조회에만 남아 있다** — Cooking 이력 조회는 6단계에서 서명을 트랜잭션 밖으로 빼서 해당하지 않는다([Cooking Spec](./cooking.md) §3.4). 서명에는 위에서 말한 상한이 걸리지 않으므로(기본 20초), IAM이 느려지면 커넥션이 그만큼 묶인다. 커넥션 풀 기본값이 10이라 상세 조회가 동시에 10건 쌓이면 다른 API까지 대기한다.

**지금 감수하는 이유**는 두 조건이 겹쳐야 하기 때문이다 — IAM 지연과 상세 조회 동시 10건. 출시 전이라 후자가 성립하지 않는다.

**고칠 시점**은 상세 조회 지연이 실제로 관측되거나 동시 사용자가 생길 때다. 고치는 방법은 응답 조립을 두 단계로 나눠 서명을 트랜잭션 밖으로 빼는 것이다 — Cooking 이력 조회가 이미 그 방식이다. Recipe는 지연 로딩 때문에 Entity 읽기가 트랜잭션 안에 남아야 하므로 호출 구조를 바꿔야 한다.

#### 실패를 감추는 경로와 감추지 않는 경로

같은 저장소 오류라도 경로마다 처리가 다르다. 기준은 **실패를 감췄을 때 사용자가 잘못된 상태를 진실로 믿게 되는가**다.

| 경로 | 저장소 오류 시 | 이유 |
|---|---|---|
| 조회 URL 발급 | URL을 `null`로 낮춤 | 이미 저장된 레시피는 그대로다. 이미지 한 장 때문에 조회 전체를 실패시키지 않는다 |
| 파일 삭제 | 무시하고 로그만 남김 | 이미 커밋된 DB 변경과 성공 응답을 되돌릴 수 없다 |
| **연결(존재 확인)** | **오류를 그대로 전파** | 여기는 저장 자체가 걸려 있다. 확인 실패를 "이미지가 유효하지 않다"로 바꾸면 사용자에게 거짓을 말하는 것이고, 저장이 실패했는데 성공으로 보이는 상태가 더 나쁘다 |

#### 발급

서명을 먼저 하고 그다음에 UploadObject를 저장한다. 트랜잭션이 원격 호출을 감싸지 않는다.

서명이 실패하면 아무것도 저장되지 않는다. 반대로 저장은 됐는데 사용자가 업로드하지 않으면 미연결 UploadObject가 남는데, 이것은 버려진 객체와 같은 취급으로 MVP에서 허용한다.

#### 연결

조건부 UPDATE 한 번으로 원자성을 확보한다.

```sql
UPDATE upload_object
SET attached_at = now()
WHERE object_key = ?
  AND user_id = ?
  AND purpose = ?
  AND attached_at IS NULL
```

갱신된 행이 1이면 성공이다. 0이면 원인을 나눠 `유효하지 않음`과 `이미 연결됨`을 구분한다. 조건을 SELECT로 먼저 확인하고 UPDATE하는 방식은 두 문장 사이에 다른 요청이 끼어들 수 있어 쓰지 않는다.

파일 존재 확인은 이 UPDATE보다 **먼저** 수행한다. 순서를 뒤집으면 확인에 실패했을 때
`attachedAt`이 이미 설정된 채로 남아, 호출부가 반드시 예외를 던져 롤백해야만 정합성이 유지되는 암묵적 규칙이 생긴다.

이 UPDATE는 **소비 도메인의 트랜잭션에 참여한다.** 레시피 저장이 실패하면 연결도 함께 롤백되어 `objectKey`가 소비된 채로 남지 않는다.

#### 해제와 삭제

UploadObject 삭제(해제)는 소비 도메인의 트랜잭션 안에서 수행하며, **요청자가 소유자인지와 용도가 맞는지를 함께 확인한다.** 존재하지 않거나, 다른 사용자의 것이거나, 다른 용도로 발급된 `objectKey`에는 아무 일도 하지 않는다.

용도까지 보는 이유는, 소유자만 확인하면 소비 도메인이 실수로 같은 사용자의 다른 용도 Key를 넘겼을 때 아직 참조 중인 UploadObject가 지워지기 때문이다. 그 뒤 커밋 후 정리가 실제 파일까지 지우고, UploadObject가 사라졌으니 재연결도 불가능해진다.

조회 URL 발급도 소유자를 확인하지만 **DB를 조회하지는 않는다.** `objectKey`가 `{prefix}/{userId}/{UUID}.{확장자}` 형식이라 발급 대상을 Key 자체에서 읽을 수 있기 때문이다. 덕분에 이미지를 볼 때마다 조회를 한 번 더 하지 않으면서도, 소비 도메인이 사용자 입력을 그대로 넘겼을 때 남의 이미지 URL이 나가는 것을 막는다.

소유자가 아니면 예외를 던지지 않고 `null`을 반환한다. 조회 실패와 같은 처리다.

저장소 파일 삭제는 커밋 이후 트랜잭션 밖에서 한 번 시도한다. 실패해도 예외를 전파하지 않고 로그만 남긴다. 삭제 성공과 파일이 이미 없는 경우를 모두 성공으로 본다.

해제는 Key를 여러 개 받을 수 있고, **커밋 후 저장소 호출은 Key 수와 무관하게 한 번**이다. 단건 해제도 같은 경로를 쓴다.

건별로 부르지 않는 이유는 커밋 후 정리가 아직 DB 커넥션을 쥔 채 돌기 때문이다. 트랜잭션 매니저는 커밋 후 콜백을 모두 실행한 뒤에 커넥션을 반납한다. 소비 도메인이 지우는 Key 수에는 상한이 없어(Recipe 삭제는 조리 이력 수만큼 사진을 지우고 이력에는 페이지네이션이 없다) 건별로 부르면 저장소가 느릴 때 요청 하나가 `건수 × 타임아웃`만큼 커넥션을 묶는다. 위의 `알려진 한계`와 같은 종류의 문제이며, 이쪽은 호출 횟수를 1회로 묶어 상한을 고정했다.

DB 삭제는 여전히 Key마다 한 문장이다. 한 문장으로 줄이려면 "실제로 지운 Key만 파일 삭제 대상에 넣는다"는 불변조건을 다시 논증해야 하는데, 로컬 DB 왕복이라 얻는 것이 적다.

## 4. 주요 설계 결정과 선택 이유

### 4.1. 서버가 중계하지 않고 클라이언트가 저장소에 직접 올린다

| 대안                         | 장점                              | 단점                                                    |
|----------------------------|---------------------------------|-------------------------------------------------------|
| 서버가 multipart로 받아 저장소에 저장  | 서버가 업로드 순간을 직접 확인할 수 있어 규칙이 단순함 | 이미지 트래픽과 메모리를 API 서버가 떠안고, 느린 회선에서 요청 스레드가 오래 점유됨     |
| **Signed URL 직접 업로드 (채택)** | 전송 부하를 저장소에 위임하면서 접근 통제는 서버가 유지 | 서버가 업로드 순간을 못 봐서, 연결 시점에 파일 존재를 따로 확인해야 하고 버려진 객체가 생김 |

### 4.2. 서비스 계정 키 파일 없이 IAM에 서명을 위임

Signed URL 서명에는 서비스 계정의 개인 키가 필요하다. 개발자 개인 계정 자격증명으로는 서명할 수 없다.

| 대안                         | 장점                            | 단점                                    |
|----------------------------|-------------------------------|---------------------------------------|
| 서비스 계정 키 파일 배포             | 서명이 로컬 연산이라 원격 호출이 없음         | 키 파일이 로컬·서버·저장소에 퍼지고, 유출되면 회수가 어려움    |
| **런타임 자격증명 + IAM 서명 (채택)** | 키 파일을 어디에도 두지 않고 IAM으로 권한을 통제 | 서명마다 원격 호출이 1회 발생하고 IAM 권한 설정이 사전에 필요 |

배포 환경은 인스턴스에 부여한 서비스 계정을 그대로 쓰고, 로컬은 개발자 계정이 그 서비스 계정을 대행한다. 두 경로 모두 최종 서명은 IAM이 수행하므로 코드는 같다.

**감수하는 대가**: 업로드 URL 발급과 대표 이미지가 있는 레시피 조회에서 각각 원격 호출이 1회 늘어난다. 조회가 잦아져 지연이 문제가 되면 서명 결과 캐시를 검토한다.

**주의**: IAM 권한을 새로 부여한 직후에는 전파 지연으로 서명이 잠시 실패할 수 있다. 처음 환경을 구성하고 바로 실행하면 권한 오류가 날 수 있으며, 대개 1분 안에 해소된다.

### 4.3. 연결 상태를 UploadObject로 서버가 소유

| 대안                        | 장점                             | 단점                                                  |
|---------------------------|--------------------------------|-----------------------------------------------------|
| `objectKey`만 도메인 컬럼에 저장   | 별도 테이블이 필요 없음                  | 같은 값을 여러 리소스에 붙이는 것을 막을 수 없고, 남의 `objectKey`도 검증 불가 |
| 저장소 파일 metadata에 소유 정보 기록 | 테이블을 추가하지 않음                   | 확인·변경마다 원격 호출이 필요하고 DB 트랜잭션으로 묶을 수 없음               |
| **UploadObject 테이블 (채택)** | 소유·용도·연결 여부를 트랜잭션 안에서 원자적으로 처리 | 테이블과 정리 책임이 늘어남                                     |

연결 여부를 DB에 두면 도메인의 저장 트랜잭션과 같은 원자성으로 처리할 수 있다. "하나의 `objectKey`는 평생 한 번만 연결된다"를 지키는 가장 확실한 방법이다.

### 4.4. 소비 도메인이 오류 코드를 결정

| 대안                          | 장점                    | 단점                                            |
|-----------------------------|-----------------------|-----------------------------------------------|
| Upload가 공통 오류 코드로 예외를 던짐    | 호출부가 단순함              | Upload가 Recipe·Cooking의 공개 계약을 알아야 하고 의존이 역전됨 |
| **결과 값을 돌려주고 호출부가 변환 (채택)** | Upload가 소비 도메인을 몰라도 됨 | 호출부마다 변환 코드가 필요                               |

Recipe는 `RECIPE_COVER_INVALID`·`RECIPE_COVER_ALREADY_USED`로, Cooking은 같은 방식으로
`COOK_HISTORY_PHOTO_INVALID`·`COOK_HISTORY_PHOTO_ALREADY_USED`로 변환한다(6단계에서 추가된 `CookingErrorCode`).
